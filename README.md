# 交换机测试工具修复版 v2

主测试程序只使用 Python 标准库，建议 Python 3.10 及以上；已在 Windows / Python 3.13 上验证。

## 开始使用

**两台电脑必须同时部署新版 `SwitchTest.py` 和 `switch_core.py`，放在同一个文件夹。新版协议不兼容旧版本。**

接收端 PC-B，监听被测有线网卡的 IP：

```powershell
python SwitchTest.py server --bind 192.168.1.20 --port 5001 --duration 600
```

发送端 PC-A，测端到端 RTT、探测失败和切换期间的连续失败：

```powershell
python SwitchTest.py echo --host 192.168.1.20 --bind 192.168.1.10 --port 5001 --frame 64 --interval 0.002 --timeout 0.05 --drain 0.5 --duration 60 --out echo.csv
```

单向打流，每条流目标为估算线速 100 Mbps：

```powershell
python SwitchTest.py flood --host 192.168.1.20 --bind 192.168.1.10 --frame 1518 --bandwidth 100 --duration 60
```

`-j 4` 表示四条独立进程流。flood 的 `--bandwidth` 是**每条流**的目标，四条流总目标为四倍。`--bandwidth 0` 表示尽快发包。接收端应运行到所有发送端完成结束总数确认后，再稍等片刻停止，以接纳仍在途的包。

只测 echo 时可用 `server --fast` 降低服务端统计开销。fast 模式不统计 flood，也不确认 flood 的结束总数。

查看明细、对比相同配置的测试：

```powershell
python SwitchTest.py gaps --csv echo.csv
python SwitchTest.py compare --a baseline.csv --b echo.csv
python SwitchTest.py bench --host 192.168.1.20 --bind 192.168.1.10 --jobs 1,2,4 --duration 3
```

bench 只测本机 `sendto` 提交能力，不统计对端接收情况，不能据此确定无丢包吞吐。网卡、实际协商速率与有线出口采用Windows界面和人工记录核对。

## 修复内容

| 问题 | 现在的行为 |
| --- | --- |
| 尾部丢失未被接收端识别 | flood 发送结束总数，接收端按每轮总数对账；结束报文重试并确认 |
| 重复包掩盖缺失包 | 稀疏位图去重，同时报告重复包数 |
| 同一源端口再次测试混入旧统计 | 每条流具有随机 session 标识，与模式、源地址一起分组 |
| 指定源 IP 绑定失败后继续测试 | 关闭 socket 并终止流，禁止自动回退到默认路由 |
| 正式阶段与收尾的超时判定不同 | 两个阶段使用同一状态机，均根据实际发送时间判断截止时间 |
| 自动放宽 timeout 却不在报告说明 | 直接使用用户设置的 timeout |
| 迟到时间从判丢时刻开始算 | 保存并报告迟到包的完整实际 RTT |
| 丢失记录淘汰后认不出迟到回包 | 利用已有每包状态和发送时间，不再维护有上限的墓碑表 |
| 收尾等待污染发包速率 | 正式发包时长与收尾观察时长独立记录，使用单调时钟 |
| CSV 与内存的抖动计算顺序不同 | 按序号计算 RTT 平滑变化，CSV 保存完整精度并按流和序号排序 |
| worker 编号取决于返回先后 | 保留进程原始编号，包括 CSV 和迟到明细 |
| UDP 载荷速率与线速目标混比 | 分开显示 UDP Mbps、估算线速 Mbps；达成率使用估算线速 |
| 子进程崩溃后父进程永久等待队列 | 轮询进程退出状态，报告未返回结果并回收进程 |
| NaN、无穷大、非法端口等参数进入测试 | 在启动网络及子进程之前校验 |

没有最终总数的接收流，只能报告“已观察序号缺口（尾部未知）”，不能给出完整丢包率。结束总数确认只证明接收端取得了分母，**不证明所有数据包已到达**。接收端随后仍会接纳乱序到达的数据包。

## 指标如何解释

echo 的“超时或本地失败”是没有在门槛内完成回显的尝试数，包含本地发送失败。不能直接当作交换机转发丢包率。`sendto` 成功仅表示内核接受了数据，不证明已在网线上发送。

RTT 按发送前的单调时间与应用读取回包的时间相减，包含两端 OS、CPU 调度、协议栈和网卡的影响。即便包早已到达内核，应用没有及时读取也可能被记为迟到。RTT 平滑变化是相邻 RTT 差值的指数平滑指标，不标称 RFC3550 单向到达抖动。

连续两包以上探测失败被列为失败段；报告的时间范围来自**实际发送时间**，表示失败探针覆盖区间以及相邻成功探针覆盖区间，不是物理故障时长的严格上下界。首尾缺少成功探针时边界不完整；尾部失败标为未观察到按时恢复。只有结合明确的拔线时刻、端口状态和切换事件，才能解释为自愈现象。

`--drain` 指定停止发包后继续观察迟到回包的时间。工具至少等到最后一包的 timeout，到达的包均已归类时会提前结束。观察结束未回包不代表永久丢失；超过观察窗口的回包无法计入本轮结果。

帧长换算假设普通未带 VLAN 标签的 IPv4 UDP、IPv4 无选项：UDP 载荷 = 帧长 − 46 字节；估算线速使用 `(帧长 + 20) × 8 × pps`，其中 20 字节计入前导码和帧间隙。64 字节帧仍对应 18 字节 UDP 载荷；新版头部 17 字节。估算线速不是网卡硬件实测值，VLAN、封装和非默认网络配置会改变开销。

降速后丢包减少只能说明问题与负载相关，不能区分交换机拥塞和端点过载。建议同一套电脑、网卡、线缆先做直连基线，再更换被测交换机，并核对网卡及交换机端口计数。内核 IPv4 丢弃计数是全网卡统计，无法归因到本测试流，零增量也不能排除接收缓冲溢出。

## 文件与架构

普通 `server` 在停止接收并打印最终汇总后，会自动导出每个 FLOOD 会话的缺失包号清单，无需增加命令参数。
例如日志是 `out/FLOOD/xxx_server.log`，清单位于同目录的 `xxx_server_missing/` 文件夹，文件名包含 session、发送端 IP 和源端口。
使用 `--no-log` 时清单仍保存到 `out/missing/`；`--fast` 不统计 FLOOD，也不生成清单。

发送端完成后，让接收端继续运行至少几秒，确认进度稳定且“未对账流”为0，再按一次 Ctrl+C，等待出现“缺失包号清单”路径。
指定了 `--duration` 的接收端会在正常到时退出后导出。直接关闭窗口或强制结束进程无法保证导出。
导出只在停止接收后进行，不在打流期间逐包写盘；大批缺失时需等待文件写完。

CSV 的 `missing_seq` 是正式包号，`session` 用来和抓包匹配。`basis=reconciled` 表示已取得发送结束总数，包含尾部缺失；
`basis=observed_prefix_tail_unknown` 表示未取得结束总数，只能列出最大已见包号之前的缺口，尾部未知。
没有缺失时生成只有表头的 CSV，控制台和日志记录“0条”。清单描述停止接收时的应用层未到达，不单独证明交换机丢包。
旧日志没有保存完整接收位图，无法通过此次升级补导历史轮次的准确缺失清单。部署本次改动时，将 `SwitchTest.py` 和 `switch_core.py` 一起复制到接收电脑。

```text
SwitchTest.py   CLI、socket 生命周期、进程调度、报告和 CSV
switch_core.py 协议、ReceiveLedger 接收去重、EchoLedger 超时与回包状态
test_switch.py 状态机、UDP 回环及 Windows spawn 多进程回归测试
test_logging.py 自动日志与中文路径回归测试
国产交换机短时测试操作规程.md 现场操作说明
tools/        抓包分析、历史结果汇总、端点诊断和报告生成脚本
docs/         架构说明、历史判据建议与需求核查
out/          测试日志、逐包记录和分析结果（保留）
WireShark抓包/ 原始双端抓包（保留）
报告/         各版报告、补充记录及相关编辑脚本（保留）
```

分析脚本已移入 `tools/`。在项目根目录运行，例如：

```powershell
python tools/analyze_flood_capture.py 发送端.pcapng 接收端.pcapng --out out/capture_analysis_new
python tools/analyze_runtime_loss.py 会话编号
```

带日期的汇总和报告生成脚本用于复核相应历史数据；运行前查看其中的数据路径及输出位置，避免覆盖已整理的分析结果。报告生成脚本需要额外的文档处理依赖。

测量状态不依赖命令行或网络 I/O，方便独立复现超时、重复和乱序情况。保持原命令入口，避免同时大幅更换使用方式。echo 会保留完整每包记录，长时间小间隔测试仍会消耗较多内存；接收端去重位图约需每个序号一位，并另有每页和每流开销。未加入磁盘流式记录或多核接收端；这些性能改造应在真实设备基线之后评估。

CSV 列：`worker, seq, rtt_us, send_s, status, late_rtt_us`。

echo 每秒进度显示墙钟时间、正式测量已运行/设定秒数及累计平均 RTT，例如：

```text
[14:32:10.125] 已运行 12.0/600s | 尝试 11,990 按时回包 11,989 超时/失败 0 在途 1 | RTT 累计均 812.4 µs
```

此行是每秒汇总，不逐包打印，避免控制台输出扰动 RTT。每包 RTT 仍保存在 CSV。累计平均不能单独用于判断当前时延趋势。server 与 flood 进度也显示运行秒数。

2026-10-12：普通服务端先回显再更新接收统计，并避免每包创建临时账本；发送端读取回包后立即取得接收时间，再解析/记账。这些调整减少软件处理对 RTT 的影响，但不能保证固定减少多少微秒。新旧版本对比需使用相同间隔、时长、预热、服务端模式及端点环境，并在每轮同步两端版本。

| status | 含义 |
| --- | --- |
| on_time | 在 timeout 内读取到有效回包，rtt_us 有值 |
| late | 回包超时，late_rtt_us 保存完整 RTT |
| unreturned | 截至观察结束未读取到有效回包 |
| send_failed | 本地 sendto 失败 |

compare/gaps 兼容原有的完整旧 CSV；旧 CSV 缺少状态与实际发送时刻，不能补回这些信息。重复或断号、不完整的明细会拒绝复算，避免静默得出好看的丢包率。gaps 优先使用新版 send_s，旧文件只能按手动传入的 interval/pps 估计。

## 验证

### 自动保存中文日志

直接运行主程序，控制台照常显示进度，同时自动生成带UTF-8编码标识的日志，默认位于out/logs，文件名包含时间戳和子命令。程序启动时显示完整日志路径。双击日志即可打开，不需要PowerShell重定向或额外启动器。

```powershell
python SwitchTest.py server --bind 192.168.214.231 --port 5001 --duration 0
```

需要指定日志位置，在子命令参数后加--log；日志已存在时拒绝覆盖：

```powershell
python SwitchTest.py server --bind 192.168.214.231 --port 5001 --duration 0 --log .\out\server_new.log
```

加--no-log可仅显示窗口。多进程流的输出也保存到同一日志。日志逐行保存，CSV仍按原方式独立输出。日志已集成在主程序，旧日志启动器已清理。

旧日志若仅打开编码错误，可选择正确编码；写入时已错误转换的乱码不能靠改变读取编码保证恢复。日志回归测试：python -m unittest -v test_logging，覆盖自动保存、控制台与错误输出、UTF-8、防覆盖及禁用日志。与测量回归测试合计20项通过。

```powershell
python -m unittest -v test_switch
```

17 项测试通过，覆盖确定性超时边界、80ms 实际延迟/50ms 超时、末尾丢包与去重、结束报文确认、不同 session、CSV 复算及原始流编号、速率口径、非法绑定/参数、Windows spawn 两流 echo/flood、子进程直接异常退出、全部流失败时非零退出状态，以及普通服务端 echo 的进度秒数和累计 RTT。所有网络测试仅使用 127.0.0.1。

尚未在真实交换机、USB 网卡、高 PPS 或拔线自愈场景验证，不能把本机回环测试结果视为设备性能验证。
